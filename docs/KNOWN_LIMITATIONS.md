# Known Limitations

Every component of the demo falls in exactly one of four buckets.

## REAL (actually implemented and running)

* Payment Intent Gateway: persisted state machine with every transition logged; money moves only after approval.
* Risk evaluation across five dimensions, fusion with versioned policy, named adjustments, counterfactual.
* Interrupt ladder T0–T4; amount-scoped holds; bank release/reject; customer cancel.
* ReasonLine: deterministic customer / analyst / audit renderings; append-only decision table (DB trigger); SHA-256 integrity hash (not a signature).
* Double-entry ledger in integer paise (system total stays ₹0; customer balances never negative).
* Incremental PathGraph; RingWatch rules with evidence; post-payment monitoring that changes the next decision.
* TaintTrace using the vendored PRIMA lineage engine (LIBR + pro rata, exact conservation, 190 ported tests).
* CircuitBreaker over WebSocket to a second browser/phone; contact responses pushed back live.
* Benchmarks and 211 automated tests.

### Added in v2 (REAL)
* **Decision Replay** — reconstructs the state leading to a decision from the recorded evidence, re-scoring each step with the same policy engine. It is a reconstruction, not a re-run against live data; if the policy file changed since the decision, the replay says so.
* **Counterfactual ladder** — deterministic re-scoring with named evidence removed/changed ("with an established recipient → Tier 2"). Shows what the *policy* would do; it does not claim the customer's situation would be safe.
* **Evidence provenance** on every signal (source, observed-at, freshness, version, status). Scenario-injected journey events are marked `simulated`.
* **SHADOW MODE** — Vigil records recommendations without intervening; compared against a deliberately conventional, hand-written bank baseline (approve / OTP step-up / decline). The baseline is a stand-in, not a model of any specific bank.
* **3D graph scene** with a frozen, precomputed layered layout (no physics) and caching.
* **Ten attack patterns** from the original project as deterministic scenarios (injected as observed ledger postings).

## SIMULATED (stand-ins for things a bank would receive from elsewhere)

* **External intelligence** — `LocalRegistryProvider` reads a local table shaped like a registry response. Labelled "SIMULATED EXTERNAL INTELLIGENCE". No DPIP, MuleHunter, I4C or DoT connection exists.
* **Call / message context** — operator-typed or scripted text, labelled "SIMULATED". Vigil cannot read calls, SMS, WhatsApp or Telegram.
* **Confirmed-scam labels** — an analyst click stands in for a verified 1930/NCRP report confirmed by the bank.
* **Bank review** — the analyst's Release/Reject buttons stand in for a fraud-ops queue; no SLA timer auto-releases holds.
* **Mule-ring transfers in Scenario 2** — injected as observed ledger postings (representing payments made before Vigil coverage), not as intents.
* **Time compression** — Scenario 3 back-dates journey events by up to 8 minutes so the story plays in seconds.
* **Pinned local hour in scripted scenarios** — while a scenario step runs, time-of-day rules (the "unusual hour" behaviour signal, 00:00–05:00 IST) see a fixed 14:00 IST, so every scenario gives the same tier whenever the demo is run. Live and ambient payments use the real hour. Each decision's audit record states which (`evaluation_context.local_hour_source`).
* **Payment rail** — simulated behind a provider port (`backend/vigil/payments/providers.py`); no gateway, no real money. A bank would plug its own rail into the same port.
* **Trusted-contact delivery** — a web page over WebSocket, not SMS/push.

## SYNTHETIC (data)

* All 142 accounts, ~2,050 historical transactions, devices and registry entries are generated by `backend/vigil/sim/seed.py` with a fixed seed. No real customer, victim or bank data.
* Thresholds and weights were hand-set to behave sensibly on this data; they are not validated on real fraud. See `MODEL_CARD.md`.

## PRODUCTION ROADMAP (not built)

* Real adapters: DPIP / MuleHunter deployment / I4C suspect registry / DoT FRI via whatever access a bank legitimately holds.
* Calibration of weights and thresholds on bank-confirmed outcomes with a temporal split; false-challenge rate as a governed metric (AdaptCal-style tuning, offline and approved).
* Authentication, authorisation, multi-tenant isolation, rate limiting (the demo API is unauthenticated and LAN-only).
* High-availability deployment, durable event stream, partitioned graph; latency SLO inside payment timeouts.
* Consent capture for trusted contacts and context signals; SMS/push delivery; localisation (Hindi and regional languages).
* Contest / re-derive workflow for TaintTrace results (designed in PRIMA docs, not built).
* PatternMemory (similarity to known ring shapes) — roadmap; the old implementation read ground truth and was not ported.
* Cross-institution tracing (value leaving the bank is reported as "left perimeter").

## Added in v11 (Vigilance) — what is real, illustrative, unvalidated

* **The procedures are illustrative.** `copilot/playbooks.py` models a bank SOP on commonly cited Indian requirements
  (PMLA STR to FIU-IND within 7 working days; RBI Fraud Risk Management Master Directions 2024, FMR within 14 days; RBI
  6 July 2017 customer liability; 1930 / CFCFRMS). It is not legal advice and not any real bank's procedure. Respond-within
  targets (15 min / 1 h / 4 h / 24 h) are demo service levels, not regulation.
* **Vigilance never acts in the bank.** Freezes, liens, STR / FMR filing, KYC and customer calls are outside steps the
  analyst ticks; the only writes Vigilance makes are its own records (ticks, acknowledge / dismiss / reopen, threads) and
  a watchlist entry after the analyst confirms.
* **Assessments and chat with Gemini can be wrong.** Classification, severity, key facts and the procedure are always
  computed by code; the model only phrases the narrative and is rejected if it names an account or posting not in the
  facts. Chat answers are not checked that way and are labelled "verify before acting".
* **Free Gemini keys are rate-limited.** When the limit is hit, answers fall back to live-data templates with a note.
* **Held-payment and coercion incidents stay open** after the bank releases or rejects (the procedure step completes;
  the incident is closed by acknowledging it).

## Added in v10 (Overview money map + Copilot) — what is real, simulated, unvalidated

* **Locations are SIMULATED.** Every account home, device position, ATM terminal and posting location is generated from
  hashes of ids (never from ground-truth labels) and shown with a *basis* and an *accuracy*: "Simulated location · ATM
  terminal · ±25 m". "Exact" in the UI means precise within the stated basis of the simulation, not a real place. Locations
  are display / investigation context only: no detector, score or payment tier reads them.
* **Attack scenarios have authored cities** for their own injected postings (e.g. the money-mule ring cashes out at ATMs
  in Mumbai; the cross-channel hub is moved from Delhi to Kolkata mid-attack so impossible travel can be shown). These
  are part of the scripted story, like the amounts.
* **Rails.** Historical seed postings keep their stored `upi`; ATM and international sinks are only *displayed* as ATM /
  international wire. New background payments use one hash-derived rail per customer (UPI or card); customers can pick a
  rail on the phone (UPI, IMPS, NEFT, RTGS, card, wallet). Per-rail limits are not enforced.
* **Onboarding cohort.** 40 legitimate new accounts (students, salaried, freelancers, shop owners) were appended after the
  main seed so the mule pipeline has ordinary new customers in it. One of them gets a high Random Forest score (new and
  active) and is never flagged because no second family agrees — see `docs/verification/regression_v10.md`.
* **Derived signals** (cash-out cluster, impossible travel, collection point, mule pipeline "suspicious path") are display
  heuristics in `config/copilot_policy.yaml`. They never change a status or a payment tier.
* **Incident severity is a hand-set rubric** (base by kind + ₹ at stake + accounts + confirmed + recency − contained). It is
  explainable (the UI shows each component) but **not validated on real data**. Confidence is shown separately.
* **The Copilot can be wrong.** Without a key it is deterministic (templates + the same read-only tools). With
  `GEMINI_API_KEY` set, briefings and chat come from Google's Gemini API and are labelled "AI-generated · verify before
  acting". It is read-only: it cannot hold, release, freeze, approve or watch anything; "watch" is a proposal the analyst
  confirms. Severity always comes from the deterministic engine, never from the model.
* **Enabling the Copilot sends incident facts off the machine** (synthetic data) to Google's API. `COPILOT_ENABLED=false`
  or no key keeps everything local. Rate limit 20 messages / minute per client, daily token cap, 2,000-character messages.
* **Attack injections bypass the payment gate**; incidents they raise come from the network watcher, and each briefing
  states which engine raised the signal.
* **India boundary.** The map uses Natural Earth's India point-of-view boundary (verified: Aksai Chin, Gilgit-Baltistan
  and Arunachal Pradesh fall inside India's outline). A production system should use a Survey of India–approved dataset.
  See `docs/THIRD_PARTY_DATA.md`.

## Other honest caveats

* Single process, single SQLite file; designed for one demo laptop.
* Customer-facing text is English only.
* The background stream is seeded but timing-dependent; nothing in the demo depends on it.
